        What lives where
        
  
        Not every record belongs in the graph. Materialize what you walk through or reason over, leave high-volume data where it already sits and link to it by ID, and keep long text in search.

    Reason code 10.4where rules and disputes meet
    Dispute runbooklong text
  
        
  
        
    
        Materialize in Neptuneyou walk through it or reason over it
        
    
        Read where it sitshuge and mostly counted, linked by ID
        
    
        Search onlylong text, a small stub in Neptune
        
  
        
  
        A record moves into Neptune when a question needs to walk through it, like an authorization that becomes part of a dispute. Neptune can also read S3 data from inside an openCypher query, so reference data can stay in S3. AWS’s own guidance takes the same line: materialize only what needs reasoning or cross-domain links.

        Who owns what
        
  
        Most of the design follows from one split. Neptune is the system of record for payment facts and how they connect. OpenSearch is a derived index that turns words and meaning into Neptune IDs.
        
  
        
    
        
      
        Neptune
        
      
        What is true, and how it connects
        
      
          
        
        • IdentityParties, instruments and the events you reason over, with deterministic IDs so reloads are idempotent.
          • 
        
        • Lifecycle chainsAuthorization to capture to settlement, refund or chargeback, as events linked by relationships.
          • 
        
        • ProvenanceSource, extraction run and ontology version on every node; chunk stubs with MENTIONS edges.
          • 
        
        • The ontology itselfA small meta-graph of classes and allowed relationships that agents can read before writing Cypher.
          • 
        
        • Questions it answersPaths, lineage, neighbors, counts over relationships.
          • 
      
        
    
        
    
        
      
        neptune_id
        
      
        Every OpenSearch document carries the Neptune ID of what it describes, plus the ontology version. That is the only join between the stores.
        
    
        
    
        
      
        OpenSearch
        
      
        Where to start looking
        
      
          
        
        • WordsFuzzy merchant names, aliases, codes such as MCCs and reason codes.
          • 
        
        • MeaningVector similarity over entity summaries, document chunks and ontology definitions.
          • 
        
        • Filtering and rankingDates, classes, access classification, relevance scores.
          • 
        
        • Document textChunk text and embeddings, which Neptune never stores.
          • 
        
        • Questions it answersWhich thing did they mean, and what has been written about it.
          • 
      
        
    
        
  
        
  
        If OpenSearch disappeared tomorrow, you could rebuild it from Neptune and the source documents in S3. Never let the reverse become true.
        

        


        
  
        OpenSearch indexes
        
  
        Three indexes, all generated from the ontology and all rebuildable. Each index name is an alias that points at a versioned index, such as entities_v1_4.
        
  
        
    
        
      
        entities one per searchable node hot tier
        
      
        Resolves names, codes and descriptions to Neptune IDs. Written only by the stream poller.
        
      
        
        
        neptune_idkeywordThe join key; also the document _id
        
        
        labelskeywordFull label chain, for class filters
        
        
        nametext + keywordFuzzy and exact matching
        
        
        aliasestextTrading names, old names
        
        
        codeskeywordMCC, reason codes, BIN ranges
        
        
        summarytextBuilt from properties and neighbors
        
        
        embeddingknn_vectorSame model as the other indexes
        
        
        ontology_versionkeywordRelease that shaped this document
        
      
        
    
        
    
        
      
        chunks one per document chunk S3 Vectors tier
        
      
        Holds the text Neptune doesn't. Written by the extraction pipeline.
        
      
        
        
        chunk_idkeywordStable per document version
        
        
        doc_id, titlekeyword, textFor citations
        
        
        texttextThe chunk itself
        
        
        embeddingknn_vectorStored on the S3 Vectors engine
        
        
        mentionskeywordNeptune IDs of entities named
        
        
        classificationkeywordAccess filter on every query
        
        
        ontology_versionkeywordFor release rollbacks
        
      
        
    
        
    
        
      
        ontology one per class or relationship hot tier
        
      
        Lets the retrieval service fetch only the schema a question needs before writing Cypher.
        
      
        
        
        irikeywordVersioned identifier
        
        
        kindkeywordClass, relationship or property
        
        
        label, definitiontextWhat text-to-Cypher reads
        
        
        domain, rangekeywordAllowed direction
        
        
        parentskeywordSuperclass chain
        
        
        cypher_patternkeywordA ready-made pattern to paste into the prompt
        
        
        embeddingknn_vectorMatch questions to classes
        
      
        
    
        
  
        
  
        Releasing a new ontology version: build the next set of versioned indexes, backfill them from Neptune and the chunk store, run the evaluation questions against them, then move the three aliases together. Rolling back is moving the aliases back.
        

        
    
        Hot tierVectors held in memory (HNSW)
      
        Query speed
        
      
        Storage cost
        
      For entities and the ontology: small, and queried on every question.
        
    
        S3 Vectors engineVectors stored in S3; text, filters and hybrid search stay in OpenSearch
      
        Query speed
        
      
        Storage cost
        
      For document chunks: large, and fine with slower vector queries.
        
  
        
  
        Bars are illustrative. For development and bursty workloads, the rebuilt OpenSearch Serverless can also scale to zero.

          Graph first, then search, then agents, with a handful of decisions settled early.
          
    
  
          

          
  
          Build order
          
  
          Get the graph right before adding search, and search right before adding agents. Each phase has a test that tells you it's done.
          
  
            
    
          1. Ontology core and generator
            Model 15 to 25 core classes: parties, instruments, lifecycle events, reason codes. Build the SHACL gate and a generator that emits Neptune CSV headers, the extraction schema and OpenSearch mappings. See how v1 is made.
            Done when renaming a class in the LinkML source regenerates every artifact, and CI fails if a committed artifact is stale.
            2. 
    
          2. Graph first
            Load one month of disputes into Neptune with deterministic IDs, plus the parties, cards and events they touch. Leave the full authorization stream in the lake. Answer chargeback lineage questions by hand in Cypher before any LLM is involved.
            Done when reloading the same month changes nothing, and the lineage queries return what your dispute team expects.
            3. 
    
          3. Search layer
            Deploy the stream poller and the entities index, then the chunks index for network rules and runbooks. Build hybrid search that returns Neptune IDs.
            Done when misspelled merchant names and bare codes resolve to the right Neptune IDs.
            4. 
    
          4. Retrieval service and agents
            Start from AWS Labs’ BYOKG-RAG, put the tools behind AgentCore Gateway and Policy, and add ontology-checked Cypher where it falls short. Collect real questions from dispute and operations teams as an evaluation set before tuning anything.
            Done when the evaluation set passes at a threshold those teams agreed to.
            5. 
    
          5. Extend
            Run code extraction across repositories at scale, publish ontology releases to other teams, and load Neptune Analytics snapshots for graph algorithms such as fraud-ring detection.
            Done when another team builds on a pinned ontology version without asking you what a class means.
            6. 
  
          

          


          
  
          Decide these early
          
  
          Each of these is cheap to settle now and expensive to change after data is loaded.
          
  
          
    
          Join in the service, not in the query
          Neptune's built-in OpenSearch full-text search works from Gremlin and SPARQL queries, not openCypher. Your retrieval service searches OpenSearch first, then passes the IDs into Cypher as parameters.
          
    
          Fork the replication poller
          AWS's Neptune-to-OpenSearch stack writes a document shape designed for that full-text search feature. Since you won't query it from openCypher, change the poller to write your entities documents instead.
          
    
          Pin one embedding model
          Entities, chunks and ontology definitions must share it. Switching models means rebuilding all three indexes, so treat it like an ontology major version.
          
    
          Version both stores together
          Stamp ontology_version on nodes and documents. New release, new indexes, alias swap. Pair it with a Neptune snapshot so a rollback covers both stores.
          
    
          Enforce access in layers
          Neptune has no row-level security. Put the rules in AgentCore Policy at the gateway, give the query role read-only IAM access, and tag OpenSearch documents with a classification the service filters on.
          
    
          Decide what lives in Neptune
          Materialize what questions walk through or reason over. Leave high-volume authorizations in the lake, linked by ID, and pull a record in when a dispute or fraud report touches it. For wider risk walks, load daily summary edges from Snowflake, such as a device seen at a merchant.
          
    
          Make long waits survive crashes
          LangGraph checkpoints save state, but a run lives in one process. Run the pipeline on Lambda durable functions instead: each step is checkpointed and retried, and a wait for a reviewer can last up to a year at no compute cost.
          
    
          Own the graph instead of using managed GraphRAG
          Bedrock Knowledge Bases GraphRAG builds its own graph in Neptune Analytics with its own entity extraction. Because your ontology is the product, you build and govern the graph; bring in Neptune Analytics later for algorithms.
