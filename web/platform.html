        7
        
    
        Build it
        Graph first, then search, then agents, with a handful of decisions settled early.
        
    
  
        

        
  
        Build order
        
  
        Get the graph right before adding search, and search right before adding agents. Each phase has a test that tells you it's done.
        
  
          
    
        1. Ontology core and generator
          Draft 15 to 25 core classes from ISO 20022 card messages, FIBO parties and agreements, and ISO code lists, then measure how many competency questions they answer. Build the SHACL gate and a generator that emits Neptune CSV headers, the extraction schema and OpenSearch mappings. See how v1 is made.
          Done when renaming a class in the LinkML source regenerates every artifact, CI fails if a committed artifact is stale, and every build prints both coverage numbers.
          2. 
    
        2. Graph first
          Load one month of disputes into Neptune with deterministic IDs, plus the parties, cards and events they touch. Leave the full authorization stream in the lake. Answer chargeback lineage questions by hand in Cypher before any LLM is involved.
          Done when reloading the same month changes nothing, and the lineage queries return what your dispute team expects.
          3. 
    
        3. Search layer
          Deploy the stream poller and the entities index, then the chunks index for network rules and runbooks. Build hybrid search that returns Neptune IDs.
          Done when misspelled merchant names and bare codes resolve to the right Neptune IDs.
          4. 
    
        4. Retrieval service and agents
          Start from AWS Labs’ BYOKG-RAG, put the tools behind AgentCore Gateway and Policy, and add ontology-checked Cypher where it falls short. Collect real questions from dispute and operations teams as an evaluation set before tuning anything.
          Done when the evaluation set passes at a threshold those teams agreed to.
          5. 
    
        5. Extend
          Run code extraction across repositories at scale, hand domain modules to their owning teams, publish ontology releases, and load Neptune Analytics snapshots for graph algorithms such as fraud-ring detection.
          Done when another team builds on a pinned ontology version without asking you what a class means.
          6. 
  
        

        


        
  
        Decide these early
        
  
        Each of these is cheap to settle now and expensive to change after data is loaded.
        
  
        
    
        Join in the service, not in the query
        Neptune's built-in OpenSearch full-text search works from Gremlin and SPARQL queries, not openCypher. Your retrieval service searches OpenSearch first, then passes the IDs into Cypher as parameters.
        
    
        Fork the replication poller
        AWS's Neptune-to-OpenSearch stack writes a document shape designed for that full-text search feature. Since you won't query it from openCypher, change the poller to write your entities documents instead.
        
    
        Pin one embedding model
        Entities, chunks and ontology definitions must share it. Switching models means rebuilding all three indexes, so treat it like an ontology major version.
        
    
        Version both stores together
        Stamp ontology_version on nodes and documents. New release, new indexes, alias swap. Pair it with a Neptune snapshot so a rollback covers both stores.
        
    
        Enforce access in layers
        Neptune has no row-level security. Put the rules in AgentCore Policy at the gateway, give the query role read-only IAM access, and tag OpenSearch documents with a classification the service filters on.
        
    
        Decide what lives in Neptune
        Materialize what questions walk through or reason over. Leave high-volume authorizations in the lake, linked by ID, and pull a record in when a dispute or fraud report touches it. For wider risk walks, load daily summary edges from Snowflake, such as a device seen at a merchant.
        
    
        Make long waits survive crashes
        LangGraph checkpoints save state, but a run lives in one process. Run the pipeline on Lambda durable functions instead: each step is checkpointed and retried, and a wait for a reviewer can last up to a year at no compute cost.
        
    
        Own the graph instead of using managed GraphRAG
        Bedrock Knowledge Bases GraphRAG builds its own graph in Neptune Analytics with its own entity extraction. Because your ontology is the product, you build and govern the graph; bring in Neptune Analytics later for algorithms.
