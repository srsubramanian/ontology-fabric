# Ontology Fabric

Ontology Fabric is the working name for a payments knowledge layer: an ontology-governed graph (Amazon Neptune, openCypher), search (Amazon OpenSearch), warehouse data (Snowflake) and agents (Claude on Amazon Bedrock, reached through MCP). So far this is a learning and design project built from public information. The next phase is a working prototype.

## What's in this repo

- `site/index.html`: the page. One self-contained file, built from `web/`: don't edit it by hand. A bar at the top switches between its four apps:
  - The platform overview (`#map`): a map of the whole system plus seven chapters, each split into sub-pages. Chapter 1 reads the ontology's coverage numbers, module owners and the Chargeback class from `ontology/` at build time.
  - The retrieval walkthrough (`#retrieval`), in 11 stages, covering Neptune, Snowflake and OpenSearch.
  - The class explorer (`#explorer`), with a question tracer. It reads the ontology from `ontology/` at build time.
  - The design studio (`#studio`), for ontology engineers and payments people (decision 24): build the ontology on its class map, on one working draft the organization shares live. Add and drag classes, drag from one to another to relate them, edit fields in the panel, or ask Claude to build in plain words; the repository's checks run on every change, and one click opens a pull request through a Claude Code session. Ask anything (decision 25): a question in someone's own words becomes a design Claude proposes on the map, as ghosts people accept or reject one by one (`#studio-ask-<id>`). Prove it: any question's query runs on an illustrative sample world in the page, openCypher on a small graph engine and Snowflake SQL on SQLite, with test cases Claude plants and checks. Each person sets how much Claude does (tutor, co-pilot or autopilot), and the studio remembers what the team accepted and rejected, and why, for Claude to read next time. Lineage (`#studio-lineage`, decision 26) starts from a meaning: every screen's fields and Snowflake columns gathered under the ontology slot they mean (`#studio-meaning-<Class>-<slot>`), with where screens disagree, or from a Snowflake column (`#studio-column-<SCHEMA>-<TABLE>-<COLUMN>`): every screen field built from it, what each means, and whose decisions a change would reopen. From a screen (`#studio-lineage-<screen>`) it traces each field through the backend and data API to Snowflake, and to what it means; both screens so far are illustrative. Each scan of the code is a version, and the view shows what a scan changed (`#studio-lineage-<screen>-changes`), bringing back a person's decision as a re-check when the code under it changes. Missions (`#studio-mission-CQ-NN`) are worked examples that coach newcomers through one open question at a time, in payments words. A business expert and an engineer work side by side: each reads in a story lens (plain sentences) or the model lens, and sees the others' pointers and selections live. Its capabilities (`db`, `user`, `sample`, `room` and the Claude Code Remote connector) make the published page organization-internal.
- `web/`: the source for the page. `web/src/fabric/` holds the bar and switches between the apps. Each app has its own folder:
  - `web/src/platform/`: the overview, with its shell (the map, section nav, reading path with each chapter's check, and router) in `shell/`, its seven chapters in `ch1/` to `ch7/`, and what they share in `shared/`.
  - `web/src/retrieval/`, `web/src/explorer/` and `web/src/studio/`. The studio reuses the explorer's model, layout and checks; its own parts are the canvas, the panel, the draft and its store, edits, placement and routing (`route.ts`), the missions with their coach (`missions.ts`, `Coach.tsx`), Ask anything (`inquiry.ts`, `Ask.tsx`), the story lens and presence (`story.ts`, `Story.tsx`, `presence.ts`), proofs on sample data (`world.ts` builds the world, `cypher.ts` and `sqlrun.ts` run queries on it, `proof.ts` picks parameters and checks a test case, `testcase.ts` has Claude write one, `Proof.tsx` shows it), the dial and memory (`memory.ts`, `useMemory.ts`, `Memory.tsx`), and lineage (`lineage.ts` reads a mapping set, `Lineage.tsx` shows it, `meaning.ts` gathers every screen's fields under what they mean and reads each column the other way, `Meaning.tsx` shows both).
  - `web/src/kit/` holds what the apps share: colour tokens, page styles, routes, Motion helpers, Prism grammars and the code block.
- `ontology/`: the ontology in LinkML (`payments.yaml`) and the competency questions it must answer. It started as an illustrative draft written down from the pages; prototype step 1 grows it into the real core, mapped to FIBO, OMG Commons and ISO 20022 at pinned releases.
- `ontology/mappings/`: mapping sets in SSSOM's TSV format, tracing a screen's fields through each layer to the warehouse and to the ontology (decision 26). One set per screen, both illustrative and shaped like the owner's stack (React, Java and Spring, a GraphQL data API with SQL in its resolvers, Snowflake). `transaction-research.sssom.tsv` answers CQ-03; it's the latest of three illustrative scans, and the earlier ones are kept in `history/`. `dispute-workbench.sssom.tsv` shows one chargeback, and shares meanings with it, disagreeing on two. The deep scan writes every version from the made-up repositories in `examples/lineage/`.
- `examples/lineage/`: made-up repositories shaped like the owner's stack (React screens, a Spring backend, a GraphQL data API with SQL in its resolvers, and a Snowflake column export), with what the scan reads for each screen (`sources/`), the files that differed at transaction research's earlier scans, what Claude Code reported reading each version (`scans/<screen>/`), and the decisions people made between them (`decisions/<screen>/`).
- `web/scripts/lineage-scan.ts`: the lineage deep scan's bookkeeping (decision 26). Claude Code reads a screen's code and reports each field's hops and meanings; the script checks every hop against the code, the SQL with sqlglot (`tools/lineage_sql.py`), the ids against the GraphQL schema, the Snowflake export and the ontology, then writes the next version, carrying people's decisions while the code under them is unchanged. `decide` writes people's accept and reject decisions into the current version. The `lineage-scan` skill (`.claude/skills/lineage-scan/SKILL.md`) walks Claude Code through a scan on the owner's desktop.
- `generated/`: everything the generator (`tools/generate.py`) makes from the ontology: OWL, SHACL, the extraction JSON Schema, Pydantic models, Neptune load headers with label chains, and OpenSearch index mappings. Don't edit it by hand.
- `docs/`: decisions, style guide, 2026 research notes, open questions, and how the project got here.
- `tools/smoke_test.py`: loads every view of every app headlessly, fails on JavaScript errors and saves screenshots.
- `tools/test_studio.py`: builds on the studio's map with the mouse and keyboard, against a stand-in for claude.ai's runtime (`tools/studio_stub.js`): places and relates classes, answers questions, asks Claude, undoes, sees another person's change arrive, asks a question and decides Claude's proposals, reads them in the story lens and comments, sees a second person arrive and follows them, proves the answer with sample data and has Claude plant a test case, proves a Snowflake question on SQLite, opens the pull request, plays two missions as a newcomer would, then answers a tutor's question and rejects a proposal with a reason the team remembers, lets autopilot prove a design before one click accepts it, traces a screen's fields in the lineage view, accepting a mapping, turning a gap into a question, and seeing what each scan changed, then starts from a meaning, follows where two screens disagree, and decides a mapping on the second screen, and starts from a column to see what a change to it reaches. First it runs `web/scripts/check-missions.ts`, which plays every mission's solution and fails if one leaves its question open or an ontology check failing, `web/scripts/check-ask.ts`, which plays the asked question in `tools/fixtures/studio_ask.json` from Claude's reply to accepted proposals, `web/scripts/check-story.ts`, which fails when the story lens can't read a relationship as a plain sentence, `web/scripts/check-proof.ts`, which runs every competency query on the sample world and the fixture's test case on the asked question's design, `web/scripts/check-memory.ts`, which checks that the team's decisions and the person's notes reach Claude's prompt and the proposals they bear on, and `web/scripts/check-lineage.ts`, which checks that each mapping set and each of its earlier versions is SSSOM, points at classes and slots the ontology has, and traces every screen field through each layer, that what each scan changed comes out as intended, that gathering the screens by meaning finds where they disagree, and that each column reaches the fields it should.
- `tools/test_lineage_scan.py`: replays the illustrative history through the deep scan (scan v1, people's decisions, v2, decisions, v3) and fails unless it writes the committed versions byte for byte (`--update` rewrites them). Then it scans a v4 change and plants mistakes in what Claude Code reports, checking the scan names each one.
- `tools/check_ontology.py`: checks that every competency question either walks real relationships, with a query that passes decision 13's checks, or names the gap in the schema that stops it, that every class has the annotations the explorer reads, that the explorer reads each class the way LinkML does, and that the class map places every class and draws every relationship without passing through a box or crossing another line (`web/src/explorer/layoutCheck.ts`, run by `web/scripts/check-layout.ts`). It prints the two coverage numbers; a question whose query fails doesn't count as answered.
- `tools/test_checks.py`: plants each kind of mistake in a copy of the ontology, checks that `check_ontology.py` names it, and that its TypeScript port (`web/src/explorer/check.ts`, which checks drafts in the browser) prints the same problems and coverage. Run it after changing either checker, and change both together.

## Working rules

- After changing the page, run `npm run check` in `web/`: it typechecks and rebuilds the page into `site/`. Then run `python tools/smoke_test.py` and look at the screenshots it names, and `python tools/test_studio.py` after changing the studio. Commit the rebuilt file with its source.
- The page is one self-contained HTML file, with fonts from Google Fonts. It builds from `web/` and inlines everything at build time, from npm packages pinned to exact versions.
- Each app's stylesheet is in the page only while that app shows, so styles never leak between apps. Import an app's CSS in `web/src/fabric/apps.tsx` with `?inline`, never as a side effect from a component.
- The overview's stylesheet (`web/src/platform/platform.css`) is still the original, and every view depends on it. Make targeted edits there; don't rewrite it wholesale.
- After changing `ontology/`, run `linkml-lint --config ontology/.linkmllint.yaml ontology/payments.yaml`, `python tools/check_ontology.py` and `python tools/generate.py`, then rebuild the page, and commit `generated/` with the change. CI fails when `generated/` is stale. Add a class's position to `web/src/explorer/layout.ts`, or the check names it and the explorer fails to load; route a relationship through waypoints there when a straight line would cross something.
- Check current facts before stating them. Standards, AWS services, the MCP spec and card network rules change often. Record sources in `docs/research-2026-09.md`.
- Label invented numbers, IDs and names as illustrative on the page.
