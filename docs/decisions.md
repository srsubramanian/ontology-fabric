# Decisions

Settled unless a later entry says otherwise. Newest changes are at the bottom of each section.

## Stores and what lives where

1. **Neptune Database (openCypher) holds the facts we reason over**: disputes, parties, instruments and the links between them. We chose it over RDF and SPARQL, since openCypher is converging on the ISO GQL standard.
2. **High-volume events stay where they are.** Every authorization and every settlement file stays in the lake or Snowflake, linked by ID. A record is pulled into Neptune when a question needs to walk through it, for example when a dispute touches an authorization. For authorizations, that means one a dispute or fraud report touches, pulled in with its capture and settlement. Risk walks that need ordinary authorizations use summary edges that Snowflake rebuilds daily instead, such as `(:Device)-[:SEEN_AT {auths, first_seen, last_seen}]->(:Merchant)`. A settlement record comes in only along such a chain; settlement files, batches and reconciliation stay in Snowflake. Fee amounts stay in Snowflake too, joined to graph records by ID; a fee program, such as an interchange category, becomes a code node only when a competency question walks to it. Warehouse-only records are still ontology classes, so decision 5's semantic views cover them: clearing batches, reconciliation and network fee collection carry `lives_in: warehouse` and `graph_load: never`, and the generator writes no Neptune load files for them.
3. **OpenSearch holds three derived, rebuildable indexes: entities, chunks and ontology.** Each sits behind an alias pointing at a versioned index, such as `entities_v1_6`. A release builds new indexes, runs the competency questions against them, then swaps all aliases in one atomic call. Entities and ontology use the fast in-memory tier. Chunks can use the cheaper S3 Vectors engine.
4. **One ID rule works across all stores**, for example `m:{merchant_id}`. The Neptune node ID, the OpenSearch `_id` and `neptune_id` field, and the Snowflake key all line up.
5. **Snowflake answers "how much" and "how often".** Metrics are defined once in the ontology and generated into Snowflake semantic views. Semantic views only see Snowflake data, so joins across stores happen in the retrieval service, by ID. The service runs a reviewed SQL template when one fits, through a connector. Otherwise Cortex Analyst, reached through the Snowflake-managed MCP server, writes SQL from the semantic views and hands it back; our validator checks it (decision 13) before the read-only SQL tool runs it, under the caller's Snowflake role.

## Ontology

6. **The ontology is a product, authored in Git.** LinkML is recommended, with Turtle as the fallback, and it's published as OWL. A generator produces:
   - Neptune loader headers and label chains, for example `:Chargeback:DisputeEvent:PaymentEvent`;
   - Pydantic models;
   - the extraction JSON Schema;
   - OpenSearch mappings;
   - Snowflake semantic views;
   - documentation.

   The generator is `tools/generate.py`, writing `generated/`. It also writes SHACL shapes (decision 8) and the OpenSearch ontology index's documents. CI fails when a committed file no longer matches the source. Snowflake semantic views wait until metrics are defined in the ontology.

   If you need OWL features LinkML can't express, keep a small hand-written Turtle file and merge it in CI with `robot merge`.
7. **Modeling rules:**
   - Model events, not status fields.
   - Make codes nodes when things link to them.
   - Give each relationship one canonical direction.
   - Keep hierarchies to 3 or 4 levels.
   - Organizations get roles rather than duplicate nodes. Role classes take plain names (`Issuer`, `Acquirer`, `Merchant`, `Cardholder`) under an abstract `PartyRole`, and a party reaches each role through `ACTS_AS`.
   - A card reaches its issuer through its BIN range (`Card IN_BIN_RANGE BinRange ASSIGNED_TO Issuer`), never a direct link, so a portfolio moving to another issuer is one edge change.
   - A chunk `MENTIONS` any entity it names, such as a merchant, a reason code or a dispute. In LinkML its range is `linkml:Any`. Who may see the chunk is still decided by its classification in OpenSearch.
8. **SHACL 1.0 core gates every load.** Missing required links reject the record. SHACL 1.2 is still a Working Draft and RDF 1.2 a Candidate Recommendation; wait until both are W3C Recommendations.
9. **Bootstrap from industry standards, then hand ownership to teams.** Chapter 1 of the platform page shows it.
   - Sources: ISO 20022 card and payment messages, FIBO for parties and agreements, and ISO code lists.
   - Align with them through `skos:closeMatch`. Never use `owl:imports`, and pin the FIBO release you mapped against.
   - Measure coverage rather than assume it, in two ways: how many competency questions the draft answers, and how many mined code terms map to a standard concept.
   - Ownership is layered. The core team owns the core, owning teams own domain modules through CODEOWNERS, and teams add their own extensions freely and promote them when shared.
   - Review windows default to a decision. Silence isn't a veto: after about five working days, the core team merges.
10. **Change lanes:**
    - Patch changes (aliases, code values) auto-merge once acceptance is 95% or higher.
    - Minor changes (new class or relationship) need owner approval.
    - Major changes (rename, remove, split) go to a change board.
    - Semantic versioning throughout. Consumers pin version ranges.

## Retrieval

11. **Pipeline stages:** gateway, understand, entry points, then four parallel lanes (walk the graph, count in the graph, ask the warehouse, find the text), then assemble, answer and check.
12. **Entry points come from OpenSearch hybrid search.** It uses min-max normalization and a weighted mean, fuzzy matching and the ontology's aliases. Neptune's openCypher has no full-text search, so the join happens in the service.
13. **Reviewed templates first, then generated queries.** Generated Cypher and SQL are validated against the ontology: labels, directions, read-only access and a LIMIT. Rejections go back to Claude with the error and the allowed options.
14. **Choose the engine by the shape of the count.** Counts that follow relationships go to Neptune. Sums, ratios and time series over big tables go to Snowflake. **The model never calculates**: numbers come from query results.
15. **Every claim cites an ID.** Before an answer leaves, code checks the citations, numbers, thresholds and data freshness, and the caller's access to every source.
16. **Reuse before building:** prototype retrieval on AWS Labs' BYOKG-RAG. We don't use Bedrock Knowledge Bases GraphRAG, because it builds its own graph from S3 documents.

## Agents and access

17. **MCP follows the 2026-07-28 spec:** stateless calls, `Mcp-Method` and `Mcp-Name` headers, `_meta`, and structured results. Agents never get a raw Cypher tool. A2A handles agent-to-agent work. Version 1 is read-only. Actions come in a later phase, once retrieval proves out: action types defined in the ontology and generated into MCP tools, such as `open_representment` taking a `Chargeback` and its `Document`s. Each calls the owning system's API, never a Neptune write, behind a Cedar permit and human approval; the change reaches the graph through the normal loads.
18. **Access is enforced in layers:**
    - AgentCore Gateway checks identity.
    - AgentCore Policy (Cedar) is default deny, and a forbid rule beats any permit.
    - Our validator comes next.
    - The IAM role for Neptune is read-only, as the last lock.
    - Snowflake enforces its own role, row access and masking policies.
    - OpenSearch filters documents by classification.

## Extraction pipeline

19. **How code becomes ontology proposals:** tree-sitter extracts facts, Claude maps them to the ontology with a confidence score, and anything under 0.9 goes to a person. Gaps become ontology pull requests.
20. **Reviews can wait for days, so runs must survive restarts.** The pipeline runs on Lambda durable functions: each step is checkpointed and retried, a crash replays past finished steps, and a reviewer's decision arrives as a callback the run waits on, up to a year, at no compute cost. Claude's mapping can use LangGraph inside a step. Each invocation keeps Lambda's 15-minute limit, so sources are split into batches, and long agent work on one repository runs as a Fargate task the function waits on.

26. **Lineage: every layer maps to the ontology, and the mappings live in SSSOM.** A business fact is renamed, converted, derived and filtered on its way from Snowflake through a data API and an application's backend to a screen. Rather than chain each layer to the next, each field maps to an ontology slot, the hub, and each hop records how it's built: the field `prov:wasDerivedFrom` the one before it, with a transform (rename, format, convert, look up, derive, add up, join, filter, or as is), a note, and where in the code it happens.
    - Mapping sets are SSSOM TSV files in `ontology/mappings/`, with the transform, its note, the code location and the code itself as declared extension columns. SSSOM is a community standard for sharing mappings, the way decision 9's `skos:closeMatch` maps to the standards.
    - A mapping Claude proposes under 0.9 waits for a person (decision 19). From the set, the studio works out each screen field's state: confirmed, proposed, waiting for a person, a gap (`sssom:NoTermFound`), or a meaning that shifts, when the field means one class and a source it's built from means another. A field derived on purpose, such as a status built from events (decision 7), maps with `skos:relatedMatch` and isn't a shift.
    - The studio shows it at `#studio-lineage`: the screen's fields lane by lane, the picked field's trace drawn as the data flows, and its classes kept bright on the map. Decisions on mappings go on the working draft and into the team's memory, and the pull request writes them into the file (a rejection as `predicate_modifier: Not`). A gap or a shift becomes a question to Ask anything.
    - A set can name the competency question its screen answers (`competency_question`, a set-level extension), and each hop can carry the code that does it (`code`). The view lights the question's walk on the map and proves it on sample data (stage 4).
    - **Each scan is a version.** A scan reads the code and the schema and writes the set again; merged, it's the next version, with `mapping_set_version`, `publication_date`, and `mapping_set_source` naming the version before. Each row says what it was read from: `subject_source` at `subject_source_version`, a repository at a commit or Snowflake's schema on a day. Earlier versions stay in `ontology/mappings/history/`, so the studio can show what a scan changed: fields new or gone, hops built differently with the code before and after, a new meaning, and code that only moved.
    - **A person's decision holds until the code under it changes.** Each field has a fingerprint of every hop, its transform and its code, but not where the code sits, so code that only moves keeps the decision. A scan that changes the fingerprint leaves the meaning for Claude to map again, and the studio shows it as a re-check, naming who confirmed it before. A decision on the draft records the fingerprint it was made on and comes back the same way.
    - **The deep scan** (`web/scripts/lineage-scan.ts`, and the `lineage-scan` skill for Claude Code on a desktop). Claude Code reads the code and reports each field's hops, with the line and code of each, and what each field and column means. The script checks every hop against the code, the SQL with sqlglot's column lineage, and the ids against the GraphQL schema, Snowflake's column export and the ontology. Then it writes the next version. A field built the same way keeps its rows, people's decisions included; a new or changed one takes Claude's mapping. The same code and the same report always write the same file. Each row records where it was read (`subject_source` at `subject_source_version`). The illustrative versions are written this way from made-up repositories (`examples/lineage/`), and `tools/test_lineage_scan.py` replays their history in CI.
    - **Git holds the mapping sets for now** (October 2026). A version reaches it through a pull request, from either a deep scan by Claude Code on a desktop or a quick refresh in the studio. A queryable lineage store is the likely home at enterprise scale, and waits.
    - The first mapping set, for a transaction research screen, is illustrative, shaped like the owner's stack: React, a Java and Spring backend, and a GraphQL data API whose resolvers hold the SQL. Its screen answers CQ-03, a transaction's whole life. Extraction from the real repositories and from Snowflake's metadata (`INFORMATION_SCHEMA`, view definitions, and `ACCESS_HISTORY`'s column lineage) fills the same format, once the repository is private. Its three scans (v1 to v3) are illustrative too: v2 adds a dispute section and reads the merchant's name the cardholder sees, and v3 adds up partial captures and lets the settlement date fall back to the capture date, which reopens both.

## The pages

21. **The learning pages move to React, one page at a time** (Vite, React 19, TypeScript, `motion/react`). Each page still builds into one self-contained HTML file in `site/`, so publishing and the smoke test don't change. Shared parts live in `web/src/kit/`. The retrieval page moved first, with every view pixel-identical to the hand-written version. The platform page follows chapter by chapter: it already builds from `web/`, its original markup and scripts moved there unchanged (every view identical), and each chapter moves to React in turn. All seven chapters moved, then the shell (map, section nav, reading path, router), each with every view identical, so the page is now all React. The class explorer and question tracer are built in React from the start.
22. **Pages read the ontology from its LinkML source, never from a hand-copied list.** The class explorer imports `ontology/payments.yaml` at build time and derives label chains, inherited slots and relationships the way LinkML's SchemaView does. Until prototype step 1 delivers the real core, that file is an illustrative draft written down from the pages themselves.
23. **One page, three apps.** The overview, the retrieval walkthrough and the class explorer build into one self-contained file, `site/index.html`, with a bar to switch between them, so there's one link to share. This replaces decision 21's one file per page.
    - Each app's routes sit under its name (`#retrieval-s4`, `#explorer-Chargeback`). The overview's stay bare (`#ch3-2`). Routes use only letters, digits and hyphens, so a shared link can open any view.
    - An app mounts the first time it shows and stays mounted, hidden, after that, so it keeps its place.
    - Only the showing app's stylesheet is in the page, so each app looks exactly as it did as a page of its own.
24. **A design studio, the page's fourth app (`#studio`), where people build the ontology on its class map.** The map is the editor, and everyone builds on one shared working draft.
    - On the map: **+ Class** and a click places a class; dragging moves one the draft added; dragging the ⊕ on a selected class onto another relates them. The panel beside it edits names, parents, owners, ID rules, standard mappings, fields and enums. A question's walk is picked by clicking its relationships, and its query is written by hand or by Claude.
    - The studio places new classes and routes new relationships itself, by the layout check's rules (`web/src/studio/route.ts`): no box on another, no line through a box or across another line, no label on a box or label, and no line along a frame's border or on top of another line.
    - Claude builds from a request in plain words, through the page's `sample` capability on the viewer's own account. It answers with a short list of edits (add a class, enum, field or relationship, or answer a question); the studio checks each one before applying it, and the whole request is one change you can undo. Decision 25 replaces this: a request now arrives as proposals that people accept one by one.
    - The working draft is one document in the page's shared store (`db`), keyed by name, so people editing different classes never overwrite each other, and changes appear live for everyone. It only adds or changes, so the studio makes patch and minor changes (decision 10); a rename, removal or split goes to the change board in the repository.
    - The repository's checks run on every change: `tools/check_ontology.py`'s rules, ported to TypeScript with the same messages (`web/src/explorer/check.ts`). `tools/test_checks.py` fails when the two disagree. Lint, the generator and the smoke test run in the pull request.
    - One click turns the whole draft into a pull request: the viewer's own Claude Code Remote connector starts a Claude Code session that applies it, runs every check and opens the pull request from `studio/<draft id>`. Then the next draft starts. The pull request's review and CI decide what merges.
    - Declaring these capabilities makes the published page organization-internal. Without them, as in a local copy, the studio still builds and checks, keeping the draft in the browser; sharing, Claude and pull requests light up where their capability is granted.
    - **Missions coach payments people with no modelling background** through one open question at a time (`#studio-mission-CQ-NN`, `web/src/studio/missions.ts`). A mission is a few steps in payments words: choose, place, connect, record fields, walk the question's path, use the query. It says why each answer is right or not, fades back the rest of the map, points at what to use next, and can show a step or do it. Each teaches one of decision 7's rules. Progress comes from the shared draft, so a mission someone else finished reads as finished. Its classes, codes and queries are illustrative first answers for the owning team to review, and `web/scripts/check-missions.ts` plays every mission to prove it answers its question and passes the checks.
    - **Problems in the ontology block a pull request; the class map's tidy-ups don't.** The studio places and routes cleanly where it can, and missions use spots and routes designed offline while they're still free. When builds crowd the map, a line through a box or two lines crossing shows as a tidy-up, and the pull request's session moves boxes and lines until the layout check passes. CI still runs it.
25. **The open-world studio: ask anything, Claude proposes, people decide.** The owner found the missions too scripted, and in an interview (October 2026) chose this direction. It's drawn at https://claude.ai/artifact/KHkFePCG7dEJmBLrTK4a95, a private page.
    - A session starts from any question in a person's own words. A business expert and an engineer work side by side on one draft, each in their own lens. Each person sets how much Claude does, from tutor to autopilot, and at every level Claude drafts and people decide.
    - Claude's payments knowledge comes from the organization's own documents: Confluence and Jira, SharePoint and OneDrive through their claude.ai connectors, and GitHub repositories read in a cloud session. Claude reads them with the asking person's own access, and every proposal cites them. The repository goes private before any internal knowledge flows into it. For now the owner wants no document connectors plugged in, so stage 3 waits and Claude works from the ontology alone. The Claude Code Remote connector, which opens pull requests, stays.
    - Quick work runs in the page; deep work (reading repositories, building sample data, running every check) runs in a Claude Code session that reports back to the draft.
    - It's built in five stages: ask anything; two lenses side by side; your documents; prove it with data; and the dial, with memory of what was accepted and why.
    - **Stage 1, ask anything, is built** (`web/src/studio/inquiry.ts`, `Ask.tsx`). One box takes a question or a request. Claude maps its words to the ontology, names what's missing, and proposes the smallest design, using three page tools through `sample`: `find_questions` to see whether a competency question asks it already, `describe_class`, and `check_design`, which runs the repository's checks on its design before it replies. Each edit becomes a proposal on the shared draft, under `inquiries`, drawn on the map as a ghost and applied only when a person accepts it. Accepting brings in what it needs; rejecting blocks what needs it. The question becomes a new competency question with its answer, or answers the open one it matches. Where a view can't run page tools, Claude answers in one call and the studio checks the design itself. Missions stay, as worked examples.
    - **Stage 2, two lenses side by side, is built** (`story.ts`, `Story.tsx`, `presence.ts`). Each person picks a lens beside the map, kept in their browser. The story lens reads the ontology as plain sentences built from the model: "Each merchant is acquired by one acquirer." What a class is, what else it's called, and whether a link is to one or many can be edited in words there, and they change the same draft fields the model lens edits. Proposals read as sentences too, and anyone can comment on one; comments live on the shared draft. Through the page's `room` capability everyone sees who else is here: their pointer on the map, a ring on what they've picked, and which lens they read in. Clicking someone goes where they are. Presence is display only, and the studio works the same alone.
    - **Stage 4, prove it with data, is built in the page** (`world.ts`, `cypher.ts`, `sqlrun.ts`, `proof.ts`, `testcase.ts`, `Proof.tsx`), so it needs no connector. A question's query runs on a sample world the studio builds from the ontology: every concrete class gets made-up instances from a seed, and a few copies of the question's own path are seeded at different times, so today, yesterday, last week, last month and last quarter each hold one. openCypher runs on a small read-only engine for the subset the competency questions use. Snowflake SQL runs on SQLite in the page (sql.js, its WebAssembly inlined), over tables built from the classes the query's table and column names map to, with Snowflake's date functions and lateral column aliases translated. Neither is Neptune or Snowflake, and the page labels the data illustrative. A test case, written by Claude or a person, plants the instances the question should find and the near misses it shouldn't, and names the rows to expect; Claude tries its case with a `try_test` page tool until it passes. Test cases live on the shared draft under `tests`. `web/scripts/check-proof.ts` runs every competency query on the sample world in CI. The design put this stage in a cloud session that reads the repositories; that can follow once connectors are back.
    - **Stage 5, the dial and memory, is built** (`memory.ts`, `useMemory.ts`, `Memory.tsx`). Each person sets how much Claude does, beside the ask box. **Tutor**: Claude adds the modelling rule behind each proposal and a question that checks the person sees why; proposals come one at a time, and the decision opens once the question is answered or skipped. **Co-pilot**: proposals to accept or reject, as in stage 1. **Autopilot**: Claude proposes, plants a test case on the design as it would be with every proposal accepted, proves the answer, and waits for one click to accept everything. At every level nothing reaches the draft until a person decides (the owner chose this over autopilot applying what passes). **Memory** is both shared and private, as the owner chose. Every accept and reject goes into the team's memory with its reason (one click on a common reason, or a few words), in shared documents, one per month, kept across drafts. Each person's setting, what they tell Claude about themselves, and their own last 60 decisions stay in their private part of the store (`data/users/<id>/studio`), which nobody else, the page's owner included, can read. Claude reads the decisions that bear on a question, and the asker's own notes, before it proposes, and searches the rest with a `recall` page tool. A proposal the team decided on before shows that decision and its reason where people decide. The page's capabilities don't change.
